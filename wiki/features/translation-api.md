# Translation API Layer

## What it does

Provides translation of individual strings from English to a target language by routing requests across three distinct Google Translate endpoints in round-robin order. If one endpoint fails, the next is tried automatically.

## Key files

- `src/main/kotlin/data/translator/TranslationRepository.kt` — interface `getTranslation(fromLanguage = "en", toLanguage: LanguageModel, query): NetworkResponse<String>`; what `TranslationManager` depends on
- `src/main/kotlin/data/translator/MyTranslatorRepoImpl.kt` — implements it; constructor takes three `TranslatorApis` (api1 HTML scraper, api2 `translate_a/single`, api3 `clients4`) plus an injectable `clock`/`cooldownMs`. **Every language uses the same endpoint list:** the two JSON endpoints (rotated) first, the scraper **always last and never in the rotation** (`endpointsInOrder()`). Keeps a per-endpoint cool-down (`ENDPOINT_COOLDOWN_MS = 60s`): an endpoint whose *request* failed is moved behind the healthy ones until it passes, so the rotation stops sending traffic to an endpoint that is refusing us (all-cooling ⇒ all still tried, no dead end). The cool-down **doubles per consecutive failed episode** (60 s, 2 min, 4 min … capped at `MAX_COOLDOWN_FACTOR` = 10× = 10 min) and resets on the first success; failures that arrive while the endpoint is already cooling (the other parallel workers of the same burst) neither extend it nor count as a new episode (`startCooldown`). Sanitizes **once**, then validates every endpoint response via `LocalizationUtils.restoreAfterTranslation` (see [string-sanitization.md](string-sanitization.md))
- `src/main/kotlin/data/translator/api_interface/TranslatorApis.kt` — interface with `getTranslation(text, langCode): NetworkResponse<String>`
- `src/main/kotlin/data/translator/apis/TranslatorApi1Impl.kt` — `translate.google.com/m` (mobile web, HTML scraping)
- `src/main/kotlin/data/translator/apis/TranslatorApi2Impl.kt` — `translate.google.com/translate_a/single` (JSON, `client=gtx`)
- `src/main/kotlin/data/translator/apis/TranslatorApi3Impl.kt` — `clients4.google.com/translate_a/t` (JSON, `client=dict-chrome-ex`)
- `src/main/kotlin/data/network/client/NetworkClient.kt` — Ktor CIO `HttpClient` singleton; `makeStringNetworkRequest(url, type): NetworkResponse<String>`, 90s timeout. **A non-2xx status is a `Failure`** (`"HTTP 429 Too Many Requests: <body snippet>"`), never `Success` text; `String.snippet()` is the shared helper that shortens a body for error messages
- `src/main/kotlin/data/network/NetworkResponse.kt` — sealed class: `Success<T>`, `Failure`, `Loading`, `Idle`; extension funs `doIfSuccess {}`, `doIfSuccessOrFailure {}`
- `src/main/kotlin/data/network/client/RequestTypes.kt` — `Get` / `Post(body)`

## State & data

- All three API impls make HTTP GET requests (URL-encoded query parameter `q`)
- Response parsing differs: API1 scrapes HTML, API2/3 parse JSON arrays
- No caching — every string hits the network (except values with nothing to translate, which are returned verbatim without a call)

## Dependencies

- `NetworkClient` (object, used by all three API impls)
- `LocalizationUtils` (used by `MyTranslatorRepoImpl` before/after each call)

- `src/main/kotlin/data/translator/TranslationManager.kt` — calls `getTranslation()` per missing key

## Notes

- Round-robin index (`lastCalledIndex`) is a **private instance field** on `MyTranslatorRepoImpl` (previously a process-global top-level `var`). Koin registers the repo as `factory`, so the index resets to 0 per translation session. Under parallel translation the increment is a benign racy write — it only nudges which endpoint is tried first.
- A per-call `ensureActive()` runs at the top of each rotation iteration so user cancellation is observed promptly.
- **`LanguageModel.onlyWebTranslate` no longer affects routing.** It used to restrict 116 languages to the HTML scraper (API1). Probed live, the JSON endpoints translate **115 of those 116** (only `itg` echoes the source back, which the manager's unchanged-output check catches), and the scraper is the endpoint Google captcha-blocks. Routing those languages scraper-only made them fail completely whenever the scraper was blocked (real run: az, km, om, pa, pt, sv, tk all failed with "translation container not found"). The flag is kept on the model but is informational.
- **The scraper used to be in the rotation (bug, fixed).** `endpointsInOrder()` rotated all three endpoints among the "healthy" ones, so every time the scraper's cool-down expired it got one request in three while Google was blocking it — visible in a real log as `Trying translation api 0 error Api1 error: translation container not found` repeating although the JSON endpoints were answering. Now only the two JSON endpoints rotate (tests: `the scraper is never part of the rotation…`, `when one JSON endpoint is cooling the other one carries the traffic…`).
- **API2 (`translate_a/single`) returns HTTP 429 to Java clients from this machine — measured 2026-09-20.** Same URL: Python (`urllib`) 768/768 × 200; Ktor CIO, plain `HttpURLConnection` (JDK 21), on both `translate.google.com` **and** `translate.googleapis.com`: 429 every time, with or without a browser `User-Agent` / `Accept` header. `clients4.google.com/translate_a/t` (API3) works from the JVM. So it is **not** an IP-wide block and **not** a header problem (**a User-Agent does not help**), and swapping to the `googleapis.com` host does not help either. Why Google treats Java clients differently on this path is **not established** (a TLS/HTTP-client fingerprint is a guess; I did not test it). Effect in a real-style run (24 languages × 71 keys, 262 s): API2 answered 0 of 25 requests, API3 answered 1720 of 1720, **1704 translated, 0 failed**, every file complete. The app copes because a 429 cools the endpoint down; the cost was 25 wasted requests. Whether API2 ever worked from the JVM is **unknown**: earlier live sweeps passed, but they did not record which endpoint answered, so API3 may have been carrying them too. Keep API2 in the list anyway: it costs one probe per cool-down and works from other networks/clients. **Consequence: at times API3 is the only working endpoint** — if Google throttles it too the run fails (the manager reports it and stops early).
- **Parse errors now say what came back.** API2/API3 turn a `JSONException` into `Api2/Api3 error: not a JSON translation (<first 80 chars of the body>)` instead of org.json's `A JSONArray text must start with '['` (which names neither the endpoint nor the cause). Together with the status check in `NetworkClient` a block page now reads `HTTP 429 Too Many Requests: …unusual traffic…`. API3's per-response debug `println("texttt=…")` was removed.
- Fallback order when an API fails: try the next endpoint in `endpointsInOrder()` (other JSON endpoint, then the scraper). If all endpoints fail for a key, the failure surfaces to `TranslationManager`, which skips that key (per-key tolerance) rather than failing the run.
- **API1 scraping:** `getTranslationData` searches for `class="result-container">` (current Google markup) then `class="t0">` (legacy) explicitly, and HTML-unescapes the extracted text (`&quot;`, `&amp;`, etc.). Previously it depended on a byte-offset coincidence in `<!DOCTYPE html>` and left entities escaped (which double-escaped `&` on write).
- **A 200 is not a good response.** If an endpoint returns text where a placeholder/tag token was lost, duplicated or invented, the markup came back malformed, or the result is blank, `MyTranslatorRepoImpl` retries with the **next token style** (`@n@` → `%n%` → `[[n]]` → `⟦n⟧`, see [string-sanitization.md](string-sanitization.md)) on the same endpoint — the endpoints return identical damage, so switching style is what helps. A *failed request* (network/HTTP/parse error) moves to the next endpoint **without** changing style, and if **no endpoint answered at all** the repo returns the `Failure` immediately: a token style can't fix "Google isn't answering", and resending every style multiplied the traffic to an endpoint that was already refusing us (a bug: 4 requests per failed request, seen as four "Trying translation api 0 error" lines per "attempt N failed" in a real run; covered by `when every endpoint fails to answer each endpoint is asked exactly once`). If an endpoint answered but every style came back damaged it returns a `Failure` too. A damaged string is never returned as `Success`.
- **Nothing to translate:** if the sanitized value has no prose (only placeholders/digits/punctuation, or an `@string/x`-style reference) the repo returns the original value as `Success` without any request.
- ~~Web-only languages depend on the HTML scraper~~ — **wrong, corrected:** an earlier version of this page (and of the changelog) said the JSON endpoints reject the 116 web-only language codes. They don't; one transient JSON failure during a 4-thread sweep was misread as "unsupported". Verified afterwards, one request at a time and with token-bearing strings, and end to end (`LiveLanguageSweepTest`: 242/242).
- **What the block looks like (verified):** `GET translate.google.com/m?...` answers **HTTP 302 → `https://www.google.com/sorry/index?continue=…`** (Google's "unusual traffic" captcha). The HTTP client follows it, the app gets the captcha HTML, and API1 reports `translation container not found`; the JSON endpoints in the same state fail JSON parsing. It is an IP-level block, not a markup change — `translate_a/single` kept answering HTTP 200 from the same machine. It clears on its own (hours); it was triggered here by running many hundreds of requests.
- **Blocking:** repeated bursts of requests can make Google return an HTML "Sorry…" block page (observed after heavy testing). `NetworkClient` now turns a non-2xx status into a `Failure("HTTP <code> …: <snippet>")`, so the endpoint cools down and the next one is tried; the manager then retries/skips the key. (Before, the status was ignored and the block page reached the parsers as "success" text, which is why the real log only showed org.json's `JSONArray text must start with '['`.) A block page that arrives with HTTP 200 still fails in the parser, now with the snippet.
- String sanitization/restoration (`LocalizationUtils`) happens in this layer, not in `TranslationManager`. Values are **inner XML** in and out (see [string-sanitization.md](string-sanitization.md)). Because API1 now unescapes HTML entities, all three endpoints return the same plain-text shape; `restoreAfterTranslation` escapes real `'` and `"` for Android.
